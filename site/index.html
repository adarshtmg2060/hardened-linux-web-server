Hardened Linux Web Server One VM. Three doors. Everything else closed.

Built to be exposed.

A bare Ubuntu/Debian VM turned into a locked-down, patchable, fully reproducible public web server — from a single idempotent Bash script. Every control here was verified from the attacker's side.

SSH: KEYS ONLY UFW: 22 / 80 / 443 TLS A+ READY FAIL2BAN ACTIVE AUTO-UPDATES ON IDEMPOTENT SCRIPT

The five hardening layers

01 / IDENTITY

Key-only SSH

Non-root admin, PermitRootLogin no, AuthenticationMethods publickey, no forwarding.

02 / NETWORK

ufw firewall

Default-deny inbound. Only 22, 80 and 443 — the three doors that are actually needed.

03 / TRANSPORT

nginx + TLS 1.2/1.3

Auto-renewing Let's Encrypt certificate, HSTS, CSP, OCSP stapling and a dedicated web user.

04 / RESPONSE

fail2ban

Three failed SSH keys in ten minutes = one-hour ufw ban. Repeat offenders get a week.

05 / MAINTENANCE

Unattended upgrades

Security pockets patched daily, unused dependencies removed, reboots left to the operator.

06 / REBUILD

One script

setup.sh with set -euo pipefail, timestamped backups and safe re-runs.

Traffic path

Internet→ ufw :22 / :80 / :443→ nginx (webuser)→ static site :640

SSH failures feed the systemd journal; fail2ban reads it and writes bans straight into ufw. Certificate renewals are handled by certbot.timer, which reloads nginx via a deploy hook.

Verified from outside

  • nmap -Pn --top-ports 200 reports only 22, 80 and 443 open.
  • Password SSH login is refused; key-based login succeeds.
  • SSL Labs reports a valid, auto-renewing certificate with HSTS.
  • /var/log/auth.log shows the bot noise that fail2ban filtered out.
  • The whole build was repeated from scratch with setup.sh alone.
